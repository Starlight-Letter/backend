# 별빛안부 — 부하 테스트 & 트러블슈팅 기록

> 도림천 세 다리에 QR로 들어와 짧은 안부 편지를 읽고 띄우는 모바일 웹 서비스.
> React 19 + TypeScript + Vite / Spring Boot 3.4 (Java 17) + PostgreSQL / AWS EC2 t3.small + S3·CloudFront

출시 전 "동시 접속 50~100명"을 목표로 11가지 케이스를 측정했다. 그 과정에서 **사이트 전체를 30초간 멈추게 하는 커넥션 풀 교착**, **하루 작성 제한이 뚫리는 경쟁 조건**, **운영 사양(2GB)에서만 드러나는 비밀번호 해시 메모리 폭주**, **데이터가 쌓이면 서랍장 집계가 커넥션 풀을 막아 사이트가 멈추는 문제**, 이렇게 네 가지 문제를 찾아 해결했다. 동시성 버그 두 가지는 **회귀 테스트로 먼저 재현**한 다음 고쳤다.

## 케이스 3. 둘러보는 100명 사이에 로그인 48건 (버그 ① 수정 후)

**상황**: 100명이 둘러보는 도중(20초 시점) 48명이 한꺼번에 로그인한다. 수정 전에는 이 순간 커넥션 풀이 바닥나 **읽기 요청까지 함께 멈추는 구조**였다.

| 구분 | p95 | 실패율 |
|---|---|---|
| 둘러보기 100명 | **6.39ms** (케이스 1: 5.44ms) | 0% |
| 로그인 48건 | 287ms | 0% |
| 전체 | 9,196건, 192 req/s | **0%** |

**결론**: 로그인이 몰려도 읽기 응답은 약 1ms만 늘어난다. 장애가 다른 기능으로 번지지 않는다.

|---|---|---|---|---|

| 위로 누르기·취소 | 7.67ms | | 남은 작성 수 | 3.82ms |

## 케이스 5. 편지 보내기 버튼 연타 (중복 제출)

**상황**: 네트워크가 느려 사용자가 "보내기"를 여러 번 누른다. 같은 `idempotency-key`로 5번 동시 제출한다.

| 기대 | 결과 |
|---|---|
| 편지 1통 | ✅ **1통 생성** (201 ×1, 저장된 결과 재응답 200 ×4) |

요청 키 행을 `ON CONFLICT DO NOTHING`으로 넣고 `FOR UPDATE`로 잠가서, 나중에 온 요청은 먼저 온 요청의 결과를 그대로 받는다.

## 케이스 6. 위로 버튼 연타

**상황**: 같은 회원이 같은 편지에 위로를 동시에 여러 번 누른다.

**결과**: ✅ 안전. `(user_id, letter_id)` 유니크 인덱스에 대한 `INSERT … ON CONFLICT DO UPDATE` upsert라서 위로는 항상 1개로 유지된다. 코드 검토와 케이스 4의 위로 누르기·취소 반복(실패 0%)으로 확인했다.

## 케이스 11. 데이터가 쌓인 뒤: 한 달 운영 분량 → 문제 ④

케이스 1~10은 편지 67통·이벤트 약 4천 건으로 쟀다. 운영하면 방문 기록(페이지를 열 때마다 1건)과 위로가 계속 쌓이고, 정리 작업이 없어 지워지지도 않는다. 서비스는 **최대 한 달** 운영하므로 한 달 분량과, 예상보다 사람이 몰린 경우인 한 달 x3을 만들어 같은 부하를 걸었다.

| 항목 | 기준(케이스 1~10) | 한 달 | 한 달 x3 |
|---|---|---|---|
| 편지 (회원 / 시작) | 67 / 60 | 5,000 / 60 | 15,000 / 60 |
| 방문 기록 (`metric_events`) | 3,931 | 500,000 | 1,500,000 |
| 위로 / 보관 | 70 / 100 | 약 5만 / 1.5만 | 약 15만 / 4.5만 |
| 세션 / 로그인 시도 / QR 통행권 | 수백 | 3만 / 3만 / 6만 | 9만 / 9만 / 18만 |
| DB 크기 | 10MB | 152MB | 441MB |

- **강물은 일부러 불리하게**: 한 달 동안 질문을 바꾸지 않아 그 달의 편지가 모두 지금 질문 하나에 몰렸다고 가정했다(`ORDER BY random()` 대상이 가장 커지는 경우).
- **위로는 일부 편지에 몰리게**(제곱 분포) 넣어 서랍장 순위가 실제처럼 갈리게 했다.
- **환경**: 케이스 10과 같은 운영 사양(백엔드·DB가 CPU 2개 공유, 백엔드 1.2GB·힙 512MB, DB 512MB, `postgres:16-alpine`).
- **부하**: 비회원 100명(홈 → 다리 → 강물 → 편지 → 서랍장, 방문 기록 포함) + 회원 50명(강물 → 편지 → 위로 상태 → 위로 → 보관함 → 띄워 보낸 흔적) + 지표 탭을 기간 없이 계속 새로고침하는 운영자 1명. 10초 동안 늘린 뒤 60초 유지했다. 백엔드를 새로 띄우고 20초 예열한 다음, 같은 조건을 2회씩 측정했다.

# 트러블슈팅 상세

## 트러블슈팅 ①: 동시 로그인 시 DB 커넥션 풀 교착

### 증상

- 동시 로그인·가입이 커넥션 풀 크기(10) 이상 몰리면 **모든 요청이 정확히 30.05초 뒤 동시에 실패**한다.
- 그 30초 동안 풀이 바닥나 **로그인과 무관한 편지 읽기 요청까지 멈춘다.** 사이트 전체 장애다.

응답이 "느린" 게 아니라 "전원이 같은 시각에 실패"한 게 결정적 단서였다. 30초는 HikariCP의 연결 대기 기본값(`connectionTimeout`)과 같다. 그래서 연산 비용이 아니라 커넥션을 기다리다 멈춘 것이라고 판단했다.

### 원인: 요청 하나가 커넥션 2개를 순차로 필요로 함

```java
@Transactional                                  // ① 커넥션 1개 점유
public SignupResult login(...) {
    limiter.consume("login-account", key, 5);   // ② REQUIRES_NEW → 커넥션 1개 더 요청
    ... hasher.matches(...)                      //    Argon2 검증(~80ms) 동안에도 ①을 쥐고 있음
}
```

요청 횟수 제한기는 로그인이 실패해 롤백돼도 시도 횟수를 남겨야 해서 `REQUIRES_NEW`(별도 트랜잭션)를 쓴다. 그런데 이걸 바깥 트랜잭션 **안에서** 불렀다.

```
풀 크기 10, 동시 로그인 16건

요청 1~10  : ① 커넥션 획득 (풀 소진) → ② 두 번째 커넥션 대기 …
요청 11~16 : ① 커넥션 대기 …
             └ 아무도 반납하지 않음 → 30초 후 전원 타임아웃
```

자원 두 개를 순서대로 잡는 전형적인 **hold-and-wait 교착**이다. 같은 패턴이 **로그인, 회원가입, 비밀번호 복구** 세 곳에 있었다. 풀 크기를 늘리면 터지는 기준점만 뒤로 밀릴 뿐이라 근본 해결이 아니다.

### 해결: 별도 트랜잭션은 바깥 트랜잭션보다 먼저 끝낸다

| 메서드 | 변경 |
|---|---|
| `login` | `@Transactional` 제거. 쓰기는 세션 한 줄뿐이라 원자성이 필요 없다 |
| `signup` | 횟수 제한 → 비밀번호 해시(커넥션 없이) → **계정+세션 저장만** `TransactionTemplate`으로 묶음 |
| `recover` | 횟수 제한을 밖으로 빼고, 코드 확인·비밀번호 변경만 `TransactionTemplate`으로 묶음 |
| `RequestRateLimiter` | "다른 트랜잭션 안에서 호출 금지"와 그 이유를 주석으로 명시 (재발 방지) |

```java
// 수정 후: signup
public SignupResult signup(...) {
    limiter.consume("signup-account", key, 5);            // 자기 트랜잭션에서 끝나고 커넥션 반납
    String passwordHash = passwords.hash(password);        // Argon2: 커넥션을 쥐지 않은 상태로 계산
    tx.executeWithoutResult(status -> {                    // 꼭 묶어야 하는 쓰기만 짧게
        jdbc.update("insert into users ...");
        jdbc.update("insert into sessions ...");
    });
}
```

부수 효과로, 비싼 비밀번호 해시가 트랜잭션 밖으로 나오면서 **요청 하나가 커넥션을 쥐는 시간 자체가 줄었다.**

### 검증

1. **회귀 테스트로 먼저 재현**: `AuthConcurrencyIntegrationTest`는 Spring 컨텍스트와 실제 PostgreSQL을 쓰고, 풀을 4개로 줄인 뒤 그 4배인 16건의 가입·로그인을 동시에 실행한다.
   - 수정 전 코드: **실패** (`CannotCreateTransactionException` ← `SQLTransientConnectionException`)
   - 수정 후: **통과**
   - 트랜잭션 프록시(`REQUIRES_NEW`)와 실제 커넥션 풀이 있어야 재현되는 버그라서, 단위 테스트가 아닌 통합 테스트로 작성했다.
2. **실서버 재측정**: 케이스 2(16·32·48명 전원 성공), 케이스 3(읽기 영향 1ms)

### 배운 점

- **"느리다"와 "멈췄다"는 다르다.** 평균 응답 시간만 봤다면 원인을 CPU나 Argon2 비용으로 오해했을 것이다.
- `REQUIRES_NEW`는 커넥션을 하나 더 쓴다. 바깥 트랜잭션 안에서 부르면 **동시 요청 수가 풀 크기를 넘는 순간** 교착이 생긴다. 한 사람이 수동으로 테스트할 때는 절대 드러나지 않는다.

## 트러블슈팅 ②: 하루 작성 제한이 동시 요청에서 뚫림

### 증상

한 회원이 서로 다른 편지 6통을 같은 순간 보내면, "한 다리 하루 3통" 제한이 있는데도 6통이 모두 저장된다.

### 원인: 확인 후 실행(check-then-act) 경쟁 조건

```
요청 A: 오늘 쓴 수 세기 → 2통 ┐
요청 B: 오늘 쓴 수 세기 → 2통 ┤ 서로의 저장을 아직 못 봄 (READ COMMITTED)
요청 A: 3통 미만이니 저장      │
요청 B: 3통 미만이니 저장      ┘ → 4통
```

개수를 세는 것과 저장하는 것 사이에 잠금이 없어서, 동시에 들어온 요청들이 모두 "아직 여유 있음"으로 판단했다.

### 해결 1차 시도: `FOR UPDATE` → 새 교착 발생

개수를 세기 직전에 그 회원의 행을 잠가 같은 회원의 작성 요청을 한 줄로 세우려 했다.

```sql
select 1 from users where id = ? for update
```

그런데 회귀 테스트가 **`ERROR: deadlock detected`**로 실패했다.

- 편지 작성은 앞부분에서 `request_keys`에 행을 넣는다. 이 테이블은 `users`를 **외래 키로 참조**하기 때문에, PostgreSQL이 회원 행에 **`KEY SHARE` 잠금**을 자동으로 건다.
- `FOR UPDATE`는 `KEY SHARE`와 충돌한다. 그래서 요청 A와 B가 각자 `KEY SHARE`를 쥔 채 서로의 `FOR UPDATE`를 기다리는 교착이 생겼다.

```
요청 A: request_keys 삽입 → users 행 KEY SHARE 획득 → FOR UPDATE 요청 (B의 KEY SHARE 때문에 대기)
요청 B: request_keys 삽입 → users 행 KEY SHARE 획득 → FOR UPDATE 요청 (A의 KEY SHARE 때문에 대기)
                                                     └ PostgreSQL이 교착 감지, 한쪽 강제 종료
```

### 해결: `FOR NO KEY UPDATE`

```sql
select 1 from users where id = ? for no key update
```

| 잠금 | `KEY SHARE`(외래 키)와 충돌 | 같은 잠금끼리 충돌 |
|---|---|---|
| `FOR UPDATE` | ⚠️ 충돌 → 교착 | 충돌 |
| `FOR NO KEY UPDATE` | ✅ 충돌 안 함 | **충돌 → 같은 회원의 작성이 한 줄로 섬** |

- 같은 회원의 작성 요청끼리만 막고, 외래 키의 공유 잠금과는 충돌하지 않는다.
- 같은 회원의 위로·보관 요청도 막지 않는다. 다른 회원끼리는 서로 영향이 없다.
- 이 행 잠금은 키 컬럼을 바꾸지 않는 용도이므로 `NO KEY UPDATE`가 의미상으로도 맞다.

### 검증

1. **회귀 테스트로 먼저 재현**: `LetterLimitConcurrencyIntegrationTest`는 `CountDownLatch`로 6개 요청을 같은 순간 출발시킨다.
   - 수정 전: **실패** (`expected: <3> but was: <6>`)
   - `FOR UPDATE`: **실패** (`deadlock detected`)
   - `FOR NO KEY UPDATE`: **통과**. 전체 테스트 38개를 **3회 연속** 돌려 불안정하지 않은지 확인했다.
2. **실서버 재현 테스트**: 수정한 코드를 별도 포트로 띄워 같은 동시 6통을 쐈다. 결과는 **201 ×3, 429 `LETTER_LIMIT` ×3**, DB에 정확히 3통.
3. **성능 영향**: 케이스 4 재측정 결과 편지 쓰기 p95 12.08ms → 14.48ms, 전체 실패 0%.

### 배운 점

- 트랜잭션만으로는 "세고 나서 쓰는" 로직을 보호하지 못한다. READ COMMITTED에서는 동시 트랜잭션이 서로의 미커밋 쓰기를 보지 못한다.
- 잠금을 추가할 때는 **이미 암묵적으로 걸려 있는 잠금(외래 키의 `KEY SHARE`)**과의 호환성까지 따져야 한다. 회귀 테스트가 없었다면 교착을 운영에서 처음 만났을 것이다.

## 트러블슈팅 ③: 운영 사양에서만 드러난 비밀번호 해시 메모리 폭주

### 증상

PC에서는 문제없던 로그인 몰림이, 운영 사양(메모리 1.2GB 제한)에서는 응답 12~19초에 메모리 한계 도달 6,203회, 스왑 640MiB를 일으켰다. 테스트가 끝난 뒤에도 메모리가 1.17GB에서 내려오지 않았다. 실제 t3.small(2GB)이었다면 스왑에 빠지거나 OOM 킬러가 Java나 Postgres를 강제 종료할 수 있는 상황이다.

### 원인 분석

1. **Argon2는 해시 하나에 19MB의 네이티브 메모리를 쓴다** (`m=19456 KiB`, OWASP 권장값). JVM 힙 밖이라 `-Xmx512m`로 막히지 않는다. 48건이 동시에 돌면 순간 약 900MB가 필요하다.
2. **glibc 메모리 할당기가 해제된 큰 블록을 OS에 돌려주지 않는다.** 스레드마다 별도 메모리 영역(arena)을 두고, 큰 블록을 해제하면 다음부터 비슷한 크기는 mmap 대신 그 영역에서 할당하도록 기준값을 자동으로 올린다. 그래서 Tomcat 스레드들이 번갈아 해시를 계산할수록 각자의 영역에 19MB짜리 블록이 남는다.
3. **누적된다.** 새 컨테이너에서 로그인 몰림을 한 번 돌리면 최고 665MiB에서 멈췄다. 하지만 **5번 반복하면 1,089MiB가 남았다.** 처음 측정이 나빴던 것도 같은 컨테이너에서 몰림을 세 번 돌린 뒤였기 때문이다. 며칠씩 켜져 있는 운영 서버는 이 누적 쪽에 가깝다.

### 해결: 두 가지를 함께 적용

| 조치 | 위치 | 막는 것 |
|---|---|---|
| `MALLOC_ARENA_MAX=2`, `MALLOC_MMAP_THRESHOLD_=131072` | `docker-compose.prod.yml` 환경 변수 | 큰 블록을 항상 mmap으로 할당 → 해제 즉시 OS에 반환. **누적 방지** |
| 동시 해시 수를 CPU 수로 제한 (`Semaphore`) | `PasswordHasher` | 동시에 계산하는 해시 수 제한 → **순간 최고치 방지**. CPU 2개에서 그보다 많이 돌려도 빨라지지 않음 |

```java
// PasswordHasher: CPU 수만큼만 동시에 계산하고 나머지는 줄을 세운다(모든 인스턴스가 공유)
private static final Semaphore SLOTS = new Semaphore(Math.max(2, Runtime.getRuntime().availableProcessors()), true);
public boolean matches(String encoded, String value) { return limited(() -> argon2.verify(encoded, value.toCharArray())); }
```

트러블슈팅 ①에서 로그인의 비밀번호 확인을 트랜잭션 밖으로 빼 두었기 때문에, 해시 차례를 기다리는 동안 DB 커넥션을 쥐고 있지 않다.

### 검증: 네 가지 설정 비교

같은 조건에서 비교했다. 컨테이너를 새로 띄우고 로그인 48명 몰림을 5회 반복한 뒤, 둘러보기 100명 + 로그인 48건을 돌렸다.

| | A. 기존 | B. 할당기 설정만 | C. 동시 해시 제한만 | **D. 둘 다** |
|---|---|---|---|---|
| 몰림 5회 후 남은 메모리 | **1,089MiB** | 172MiB | 1,087MiB | **159MiB** |
| 순간 최고 메모리 | 1,200 (한계) | 737MiB | 1,200 (한계) | **239MiB** |
| 메모리 한계 도달 | **2,416회** | 0 | 2,140회 | **0** |
| 스왑 사용 | **345MiB** | 0 | 258MiB | **0** |
| 둘러보기 p95 | 79.7ms | 56.9ms | 17.3ms | **10.7ms** |
| 로그인 p95 | 1.23초 | 1.11초 | 1.77초 | 1.22초 |

- **B만 적용하면** 누적은 막지만 순간 최고치가 737MiB까지 튄다.
- **C만 적용하면** 순간 동시 계산은 줄지만, 할당기가 메모리를 돌려주지 않아 누적이 그대로다.
- **D(둘 다)**에서만 메모리가 2GB 서버 안에서 넉넉하게 유지된다. 둘러보기 응답도 가장 빠르다(해시가 CPU를 독차지하지 않아서).

### 배운 점

- **PC에서 통과한 부하 테스트는 운영 사양에서 다시 해야 한다.** 이 문제는 메모리가 넉넉한 PC에서는 전혀 드러나지 않았다.
- `-Xmx`는 JVM 힙만 제한한다. 네이티브 라이브러리(Argon2, 압축, 암호화 등)의 메모리는 컨테이너 메모리를 직접 잡아먹는다.
- 같은 테스트도 **처음 한 번과 반복 후의 결과가 다를 수 있다.** 누적형 문제는 반복 측정해야 보인다.
- 원인이 두 겹이면 조치도 두 겹이 필요하다. 하나씩 끄고 켜서 비교(A~D)해야 각 조치가 무엇을 막는지 증명할 수 있다.

## 트러블슈팅 ⑤: 측정 스크립트 함정 (실패율을 믿기 전에 스크립트를 의심하기)

## 트러블슈팅 ⑥: 데이터가 쌓이면 서랍장 집계가 커넥션 풀을 막음

### 증상

- 한 달 분량에서 서랍장(`GET /best`)만 p95 4.8ms → 134~149ms로 30배 느려졌다.
- 한 달 x3에서는 사이트 전체가 멈췄다. 처리량 167 → 25 req/s, 서랍장과 상관없는 강물·편지 열기도 수 초~30초, 일부는 **정확히 30초**에 실패했다.
- 그런데 `docker stats`의 CPU는 낮았다. 바쁜 게 아니라 **무언가를 기다리고 있다**는 신호였다.

### 원인 분석

부하 중에 `pg_stat_activity`로 실행 중인 쿼리의 대기 상태를 찍었다.

```
 IO     | BufFileRead  | 8 | SELECT l.id::text, l.bridge_id, l.body, ... (서랍장)
 IO     | BufFileWrite | 5 | SELECT l.id::text, l.bridge_id, l.body, ... (서랍장)
```

`BufFileRead/Write`는 **디스크 임시 파일**을 읽고 쓰는 대기다. `EXPLAIN (ANALYZE, BUFFERS)`로 확인했다.

```
Sort Method: external merge  Disk: 3816kB      ← 위로 15만 건을 편지 본문까지 붙여 정렬
Sort Method: external sort   Disk: 3808kB
Buffers: temp read=10929 written=2735
Execution Time: 124.728 ms
```

1. 서랍장 쿼리는 위로를 편지와 **먼저 조인한 뒤** `GROUP BY l.id, q.body`로 묶었다. 그래서 집계 중간 결과에 편지 **본문**(수백 바이트)이 위로 수만큼 실린다.
2. 그 크기가 정렬 메모리(`work_mem` 기본 4MB)를 넘으면 PostgreSQL이 **디스크로 넘겨 정렬**한다. 쿼리 하나가 느려지고, 그동안 커넥션을 쥐고 있다.
3. 서랍장은 비회원이 한 바퀴 돌 때마다 부르는 화면이다. 느린 서랍장 쿼리가 **커넥션 풀 10개를 모두 차지**하면, 나머지 요청은 커넥션을 기다리다 30초(`connectionTimeout`) 뒤 실패한다. 트러블슈팅 ①과 같은 "느림이 아니라 멈춤"이다.

같이 찾은 작은 문제도 있었다.

| 위치 | 문제 | 영향 |
|---|---|---|
| 편지 하나의 위로 수 세기 (`/letters/{id}/engagement`, 위로 누르기, 띄워 보낸 흔적) | `reactions`의 인덱스가 `(user_id, letter_id)`·`(activated_at, letter_id)`뿐이라 `letter_id`만으로는 못 씀 → **편지를 열 때마다 위로 테이블 전체를 읽음** | 한 달 2.3ms → x3 7ms, 데이터에 비례 |
| 지표 화면 (`/admin/metrics`) | 이벤트 종류마다 쿼리를 따로 보내 **방문 기록 테이블을 6번** 읽음. 기간 조건도 `(? is null or created_at >= ?)` 형태라 계획이 복잡해짐 | 한 달 215~271ms → x3 1초 이상 |
| 다리 화면의 편지 수 | `where question_id = ?`만 있어서 `(bridge_id, question_id, …)` 인덱스의 앞 칸을 못 씀 | 인덱스 전체 훑기 |

### 해결

| 조치 | 위치 | 효과 |
|---|---|---|
| **집계를 먼저, 본문은 나중에**: 위로를 `letter_id`로만 묶어 순위를 정하고, 상위 후보에만 본문을 붙인다 | `JdbcEngagementService.best` | 정렬할 데이터가 (id, 수, 시각)으로 작아져 **디스크 임시 파일 0**. 125ms → 60ms |
| **순위 집계 10초 캐시**: 같은 범위·기간 요청이 몰려도 `ConcurrentHashMap.compute`로 한 번만 집계 | 같은 곳 | 대부분의 서랍장 요청이 DB 집계를 건너뜀 |
| **본문·공개 상태는 매번 새로 읽기**: 캐시하는 건 (편지 id, 반응 수) 후보 20개뿐 | 같은 곳 | 임시 숨김·삭제는 캐시와 상관없이 **즉시** 빠지고 순위 번호도 다시 매김 |
| `reactions (letter_id) WHERE active`, `saves (letter_id)` 인덱스 | `V017__engagement_letter_indexes.sql` | 편지별 위로·보관 수가 인덱스로 바로 찾아짐 |
| 지표를 **한 번 읽어** `(event_type, bridge_id)`로 묶은 뒤 자바에서 나눔. 기간이 없으면 조건 자체를 뺌 | `JdbcSurveyMetricsService.summary` | 테이블 읽기 6회 → 1회 |
| 편지 수 조건에 `l.bridge_id = b.id` 추가 | `BridgeQueryService.get` | 인덱스를 앞 칸부터 사용 |

```java
// 수정 후: 순위(작은 값)만 집계·캐시하고, 본문은 상위 후보에만 매번 붙인다
SELECT r.letter_id, count(*) AS reaction_count FROM reactions r JOIN letters l ON l.id = r.letter_id
WHERE r.active AND r.activated_at BETWEEN ? AND ? AND l.status = 'published' AND (? IS NULL OR l.bridge_id = ?)
GROUP BY r.letter_id ORDER BY reaction_count DESC, max(r.activated_at) DESC, r.letter_id LIMIT 20
```

캐시 때문에 **반응 수·순위는 최대 10초 늦게** 반영될 수 있다. 기능명세서 F-05에 이 내용을 적었다. 반대로 "숨김·삭제는 즉시 빠진다"는 원칙은 본문을 매번 새로 읽어서 지켰다.

### 검증

1. **결과가 같은지**: 수정 전후 쿼리를 한 달 x3 데이터에서 5가지 조합(전체·다리별, 최근 30일·7일·1일)으로 실행해 **순위 10개가 모두 일치**했다.
2. **회귀 테스트**: 실제 PostgreSQL에 붙는 통합 테스트 2개를 추가했다.
   - `EngagementIntegrationTest.ranksBestByReactionsAndDropsHiddenLetterEvenWhenCached`: 위로 수 순서·다리 범위, 그리고 **캐시가 살아 있는 동안 1위 편지를 숨겨도 바로 빠지고 순위가 1·2·3으로 다시 매겨지는지**
   - `SurveyMetricsIntegrationTest`: 한 번 읽어 나눈 결과가 종류·다리·비회원/회원·기간별로 맞는지, 다리 없는 기록이 마지막에 오는지
3. **부하 재측정**: [케이스 11 수정 후](#케이스-11-데이터가-쌓인-뒤-한-달-운영-분량--문제-) 표. 한 달 x3에서 25 → 168 req/s, 실패 0%.

### 배운 점

- **데이터가 적을 때의 부하 테스트는 "지금"만 보장한다.** 케이스 1~10은 모두 통과했지만, 같은 코드가 한 달 x3 데이터에서는 멈췄다. 쌓이는 테이블(방문 기록, 위로)을 먼저 찾고 그 양을 넣어 재야 한다.
- **CPU가 낮은데 느리면 기다리는 것이다.** `pg_stat_activity`의 `wait_event`를 보면 무엇을 기다리는지(디스크 임시 파일, 잠금, WAL) 바로 보인다.
- `GROUP BY`에 넓은 컬럼(본문)을 같이 실으면 집계 중간 결과가 커진다. **좁은 키로 먼저 줄이고, 넓은 데이터는 마지막에 붙인다.**
- 캐시는 "무엇을 캐시하지 않을지"가 더 중요하다. 순위만 캐시하고 공개 상태는 매번 읽어서, 운영 정책(숨김 즉시 반영)을 깨지 않고 부하만 줄였다.

## 한계와 다음 단계

- 운영 사양은 Docker의 CPU·메모리 제한으로 **흉내 낸 것**이다. 실제 EC2 vCPU는 PC 코어보다 단일 코어 성능이 낮을 수 있어서, 배포 후 운영 환경에서도 한 번 측정할 계획이다.
- **CPU 크레딧 대비**: 인스턴스가 T3 Unlimited 모드인지 확인한다(T3 기본값). `CPUCreditBalance` 경보를 걸고, 행사처럼 몰림이 예상되는 날에는 일시적으로 인스턴스를 키우는 것을 검토한다.
- **DB 백업이 없다.** EBS 스냅샷 자동화(Data Lifecycle Manager)나 `pg_dump` → S3 cron을 출시 전에 설정한다.
- **모니터링·알림이 없다.** CloudWatch 경보(CPU, 상태 검사, CPU 크레딧 잔량)를 추가한다.
- 운영 정적 파일에 `Cache-Control` 헤더를 추가한다. 운영 compose의 DB 포트 매핑은 `127.0.0.1:5432:5432`로 좁힌다.
- t3.small에서 서버가 직접 `gradlew bootJar`로 빌드하면 빌드 중 메모리를 서비스와 나눠 쓴다. 이미지 빌드를 CI로 옮기는 것을 검토한다.
- **오래된 데이터 정리 작업이 없다.** 세션·로그인 시도·QR 통행권·방문 기록이 쌓이기만 한다. 케이스 11에서 한 달 분량(DB 152MB)으로는 문제가 없음을 확인해 이번 운영 기간에는 넣지 않았다. 운영을 연장하면 만료된 세션·통행권 삭제와 방문 기록 월별 집계를 추가한다.
- 서랍장 순위 캐시는 서버 메모리에 있다. 지금처럼 백엔드가 한 대일 때만 맞는 방식이라, 여러 대로 늘리면 서버마다 최대 10초씩 다른 순위를 볼 수 있다.
